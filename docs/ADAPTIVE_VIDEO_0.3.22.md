# 按实测链路与设备负载调节画质（0.3.22）

## 行为

取消操作时固定长边360/350kbps的策略。点击、返回、拖动和视频播放使用同一份自适应分辨率与码率预算，输入提示仅记录交互上下文和取消过时补帧，不能直接降画质。交互状态切换而编码参数未变时，不重复设置编码器，也不因为松手就强制再发关键帧。

优先级为流畅、低延迟，然后提高画质。保持最高30fps、采集时隙、接收端VSync、纹理缩放、原生硬编/硬解、有限队列和最新帧策略；不增加逐帧CPU像素分析、运动模糊或重型软件编码。实际帧率仍受内容及设备限制。

正常请求从原屏每边85%提高为约90%，长边最高2400。1080×2400的应用目标约970×2160（偶数向下取整），原生编码器还可能进一步对齐或自适应缩放。直连/UDP从4Mbps起步，UDP中继3Mbps起步，正常上限最高16Mbps；TCP/未知中继从2Mbps起步，允许在实测健康时逐步达到8Mbps。上限不是固定发送量，也不是保证所有设备、路径达到该值。

## 下降条件

采集到新的统计证据后，分别处理链路和设备压力：

- 链路：相对当前路径基线的媒体/控制ICE RTT增长、丢包、发送积压、接收抖动缓冲积压。普通压力需持续2个新样本，发送积压>120ms、缓冲>250ms或丢包>10%则首个有效样本即可保护；码率退降至少间隔2秒。
- 真实带宽不足：WebRTC报告bandwidth限制，同时源帧率与发送吞吐存在持续缺口，且估计尚未达到应用上限。弱估计、bandwidth标记或操作事件本身不能单独降档。
- 应用上限造成的限制：估计已顶到当前上限、编码/解码/显示耗时有实测余量、仍有实际发送时，先有界试升预算。达到最终上限仍持续跟不上，则减小像素，避免反复试升到无界高码率。
- 设备：实测编码、解码、绘制、换缓冲或额外处理排队持续超标；或者发送正常但解码/显示吞吐持续跟不上。连续3个新样本才降一级，最小间隔3秒。已确认网络受压时，不把网络造成的接收帧率下降重复算成设备保护。

链路像素比例为1、1.25、1.5、2、3、4、6；设备比例为1、1.25、1.5、2、3，两者取更保守的一项，不相乘进行双重压缩。极弱链路仍可能退到很低的清晰度，这只由持续实测压力触发。应用码率预算最低150kbps，实际发送可以更低，minBitrate仍为0。

## 回升条件

普通预算试升要求真实链路估计达到当前预算附近、两端处理成本有余量、连续实际帧节奏健康；累计4个新样本上调约20%，受路径最终上限约束。不会把估计再乘折扣后不断写回最大码率，从而自我压低到谷底。带宽估计缺失时不虚构60Mbps，静止的廉价帧也不证明可持续30fps。

源内容达到12fps以上时，以min(源帧率,目标帧率)作为节奏参考，发送、解码、显示至少跟上其80%，持续4秒才确认健康，允许稳定12/24fps视频证明自己的真实节奏。分辨率变更后重新积累节奏证据。

链路分辨率恢复要求连续8个有余量样本、至少8秒间隔，并核对下一档像素增长后的预计处理成本；设备分辨率恢复要求连续10个有余量样本及至少10秒间隔。未知、过期、重复或间隔过长的统计不能凑恢复时间。接收反馈最多使用1.5秒，设备成本和实际帧率缺失时保留现档。静止补帧仍有次数上限。

## 诊断与验证边界

诊断显示目标输出尺寸、应用预算上限、最高帧率及链路/设备保护状态；实际编码尺寸、发送/接收速率仍在原统计中。原“估计可用”改为“本机发送带宽估计”，避免误认为宽带测速或控制端接收容量。

回归覆盖60Mbps估计健康试升、低估计但无压力不误退、残留cpu标记、应用上限诱发的带宽限制、到上限仍掉帧、真实排队与丢包、接收解码/显示瓶颈、12/24fps媒体、缺失与旧统计、恢复迟滞和下一档像素成本，以及输入和状态切换不触发低清。构建与签名回执见 `../artifacts/BUILD_0.3.22.json`。

WebRTC AAR与0.3.21相同，没有重建库；原生库/内部音频类保持不变，沿用相同AAR的0.3.20调度、采集桩和队列回执。本次修改应用策略及诊断，未部署服务端、未安装或测试手机。模拟统计与单元测试不能证明真实主观画质、帧率或端到端延迟。

两端覆盖安装 `../artifacts/SimpleRC-0.3.22-debug.apk`，选择“新策略”后重新连接。建议对照持续播放视频、快速滑动、正常读字和设备长时间发热后的实际发送/解码/显示帧率与保护状态。
