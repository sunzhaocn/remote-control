# 0.3.32 静止精修与诊断复核

接受用户对0.3.31的B项复核：带宽估计与应用上限不是同一概念，精修不应自行把当前4Mbps上限变成530kbps。0.3.31中“精修预算受BWE约束”的实现过于激进，本次明确更正。仍只修改应用层，保留30fps和各构建的固定尺寸规则，不改AAR、原生库、权限或后端。

## A：选择准确标注观测状态

本次选择第二个方案：设备压力仅用于观测、限制/撤回试升，不主动改变像素或帧率。诊断由“设备保护”改为“设备压力（仅观测，固定尺寸/帧率；限制或撤回试升）”，类注释也说明内部scale只是恢复证据档，不能当成实际降画质动作。

没有新增一次性75%/60%性能档、机型缓存或动态降帧。它们会改变当前固定90%/88%/80%的产品规格，且目前没有OPPO Android11/vivo Android16前10秒的真实流水线分布。该选择只修正诊断含义，没有解决设备持续过载本身：过载仍可能由有界队列丢帧，不能宣称已经实现设备侧主动负载调节。

## B：精修只抬不降现有上限

`StillRefinementBudget`先按路径最大值约束现有上限，再与 `0.85×BWE−音频/控制预留` 的计算值取较大者。计算出的新增精修目标最多8Mbps；若已经稳定运行在12Mbps，则保留12Mbps，不因8Mbps精修增量界限降档。路径最大值仍是硬约束。

例子：current=4M、BWE=1M，精修上限维持4M；current=300k、BWE=1M，可尝试530k；current=12M、路径上限16M，保持12M。BWE缺失不授权提高现有上限。RTP最低码率仍为0，保留拥塞控制和发包节奏，维持上限不代表强迫发送到该速率。降码率仍由实际压力路径处理。

## C：静止质量前置判断与两次失败暂停

新增`StillRefinementGate`，只管理静止精修：

- 只接纳静止阶段已持续至少500ms后的新QP区间样本；样本最近3秒有效。前置判断仅用于H.264且0<QP≤51，避免拿不同编码格式的QP量表横比，也不把运动/视频的高QP移植到静止画面。
- 静止QP>32且估计可用于视频的预算<2.5Mbps时，暂不开始新的精修。估计预算取本次上限与`0.85×BWE−预留`较小者，仅用于是否值得尝试的判断，不写成更低的发送上限；因此B修复后current=4M/BWE=1M仍可判断余量不足。
- 该前置判断会在新的低QP、足够带宽余量、真实内容恢复/用户操作、路径或会话变化时解除。没有QP不虚构“不可达”；这是一条保守启发式，不是对字体可读性或QP必然可达的证明。
- 连续两次实际静止精修失败后，暂停后续静止精修，不再依靠10/20/40/60秒到期反复重试。已知失败时BWE，则达到该估计的两倍可重新开放；失败时没有BWE，则等待新的有效估计至少4000kbps。实际路径变化或新会话也清除暂停。开放后仍遵守已有活动迟滞、刷新预算及安全等待。
- 第一次静止精修失败仍有10秒文本专用冷却；成功确认清除文本失败记录，触摸取消不当成失败。文本失败不设置连续视频的requiresValidation、不增加连续视频失败惩罚。连续视频自己的试验失败、迟到压力和观察期保护保持。
- 文本精修暂停不削减正常预算、分辨率、帧率，也不限制正常视频试升。诊断会说明暂停原因及等待带宽/路径条件。

这是有意的尝试抑制，不承诺暂停后当前静止画面一定达到QP≤28。基础画面照常传送；需要更清楚时仍取决于实际网络与编码能力。

## D：诊断边界与无效目标

- 通过qpSum差分得到的0.0不再显示成“QP均值0.0”，改为未知。该处理只影响应用统计及前置判断，未修改AAR中的编码器回调。
- VIDEO_FEEDBACK的senderPolicy在发送、接收端统一使用768字符上限，先过滤控制字符。旧端仍可能按512截断，完整显示需要两端都升级。
- 文本试验不再把内部scale强制改为1.0，也不要求它代表像素增长；精修只调整码率上限。实际目标尺寸仍来自固定比例输出计划。
- 保留applied尺寸、采样新鲜度、解码尺寸与完成swap进度校验。即使产品固定尺寸，旧反馈、丢失帧和错误尺寸也可能出现；它们是接收验证，不应作为死逻辑删除。非文本试验的增长一致性检查保留。

## 验证与交付

测试覆盖：4Mbps不被精修降至530kbps、已有12Mbps预算保持、低预算小步提高、未知BWE；0QP未知及恢复有效统计；768字符两端一致与控制字符过滤；高运动QP不触发静止前置暂停，新的静止高QP可以抑制无效请求；两次失败不会周期重试、带宽翻倍/路径变化解除暂停、正常视频试升不被文本暂停锁住、文本成功重置自己的失败记录；固定尺寸仍拒绝错误解码形状，正常视频迟到失败保留验证锁。
