# 优化清单核对与采用结果（0.3.31）

依据 `OPTIMIZATION_CHECKLIST.md` 与当前源码逐项核对。原清单保留不变。本次采用能由现有链路与回归测试支持的部分，不把清单里的耗时估算当成双机测量结果。正式版仍保留90%宽高、30fps；88%与80%构建保持各自固定比例。旧0.3.30及两个对照APK保留，可继续比较。

## 已实施的变化

- 操作、静止、视频统一输出尺寸，正式版也不再因交互租约、2400长边上限或旧保护档切换编码尺寸。旋转/共享屏幕几何变化仍正常更新。未加入操作时固定乘0.6的码率限制。
- 静止精修启动时按 `min(8Mbps, 路径上限, 0.85×BWE−音频/控制预留)` 计算预算；BWE缺失或无效时不授权提高现有预算。应用上限最低150kbps，RTP最低码率仍为0，不强迫网络发送150kbps。活动中的一次精修预算保持，不把受自身限码率影响的BWE逐样本反复乘0.85，避免递归掉档。真实压力仍立即取消/回退。
- 静止精修最多12次补帧、间隔200ms，原生确认完成立即停止，不再强制至少12次或最多24次。保留原生“低QP确认，或QP未知时至少8个编码输出”的兼容路径；视频恢复立即取消静止补帧。请求次数不代表一定编码/发送/显示了同样多帧。
- 应用主动清晰刷新请求合并到一个待处理标志，任意10秒最多接纳3个，超额等待；发送排队>50ms或新丢包报告>3%时取消补帧并暂停新请求至少1.5秒。预算不足时不启动需要刷新验证的新试验。编解码器启动、远端PLI/FIR和原生丢帧恢复不受这个应用请求预算拦截。
- 严重排队/缓冲/丢包保持原有高阈值，但新样本与再次退降间隔可缩至500ms；普通压力保留双样本确认与2秒退降间隔。应用层控制PONG包含两端主线程调度，取消把它的增长直接当成媒体网络拥塞的依据；媒体ICE RTT、实际排队、丢包、接收缓冲仍参与判定。
- 诊断增加区间QP均值、有效bpp、编码/解码关键帧累计数、输出尺寸变更、采样观察到的编码尺寸变更和应用刷新请求数。发送侧摘要同步到控制端已有策略栏。缺字段显示未知，无新编码帧不计算bpp；变尺寸区间不混算bpp。输入到显示延迟明确标为未标定。

## 逐项结论与理由

| 项目 | 结论 | 原因与具体范围 |
|---|---|---|
| P0-1 交互期固定尺寸 | 采用尺寸部分 | 正式版、80%、88%均全程固定本配置的比例，解决交互前后尺寸切换。拒绝固定乘0.6码率：用户此前明确要求带宽/性能充足时不能一操作就变糊，现有拥塞保护已能在有实测压力时限速。不能据此承诺消除150–400ms卡顿，该数字尚未在用户手机测量。 |
| P0-2 15秒驻留、48%下限 | 不采用 | 会改变当前固定90%及80%/88%对照规则。低分辨率有时更易编码，但同码率下65%必然比90%文字更清楚并非通则，缩小本身会损失细字。需要同一页面、字体、编码器和限速条件下的实测后再选长期档位。 |
| P0-3 fps优先30/24/20/15 | 不作为默认采用 | 与用户要求的稳定30fps节拍及优先流畅度冲突。15fps会把新画面采样间隔拉到约67ms；24fps在常见60Hz下也需要不同节拍适配。改fps不一定重建编码器，但仍会改变输入、发送和显示节奏；不能宣称优先降fps总是最优。 |
| P0-4 按bpp反推码率 | 采用诊断，不采用硬指标限码率 | bpp可以帮助比较，不能用0.10或0.06保证文字/视频质量：运动、静止预测、字体和编码器都会改变所需码率。硬性最低1.2Mbps与窄带低延迟冲突；BWE是估计，不能凭像素数制造可用带宽。继续由实际拥塞与设备反馈决定发送预算。 |
| P0-5 静止精修预算/补帧 | 部分采用并修正 | 取消无条件8Mbps、强制至少12次和最多24次；采用带宽约束、压力暂停、最多12次并完成即停。拒绝`max(2M,1.5×BWE)`作为网络上限：低带宽时会高于可用带宽。拒绝直接6次：现有未知QP兼容路径需要至少8个真实编码输出，还要容纳少量丢弃。保留逐级失败冷却，避免每10秒反复失败。精修本来已受实际输出计划约束，并不会在现有90%/80%/88%配置下变原生尺寸。 |
| P1-6 拥塞响应提速 | 部分采用 | 严重情况500ms退降，并剔除控制主线程PONG这一混淆源。普通情况仍需连续证据：将所有100ms缓冲/单次丢包都立刻判为拥塞，会惩罚稳定高RTT路径，重现误判和掉档。500ms是允许再次评估/退降的时间，不是手机上已经验证的端到端响应承诺。 |
| P1-7 记忆安全档、删除观察期 | 保留现有保护 | 旧安全档不代表换路径、设备升温后的安全档。此前已专门修复刚确认又失败、长期低清和来回跳；删除观察与失败冷却会撤掉这些保护。清单“150kbps起每档只有20%”的推导也忽略了现有每步至少加100kbps等路径，不能直接据此证明必然一分钟。保留小步试升、真实接收/显示进度、失败回退和观察期。 |
| P1-8 队列3→2、帧龄66ms | 暂不采用 | 3是最多在途帧数，不等于每帧必等100ms。仅凭平均encodeMs>20ms判断流水线深度不可靠，盲缩队列可能造成额外丢帧。原始SurfaceTexture时间戳存在可选对齐，直接减System.nanoTime或按66ms丢弃，需要先验证时钟域及正常设备的分布。强制补帧必须使用新时间戳，否则会被适配器/编码器拒绝；本次不动AAR及这条已验证兼容链路。 |
| P1-9 原生接收缓冲100ms | 暂不采用 | 当前Java接收器没有对应可直接设定的硬上限接口；原生playout delay目标不自动等价于严格最大缓冲。重传、参考帧依赖和解码截止策略需一起验证。没有5%丢包双机曲线前，硬砍缓冲可能把延迟变成花屏和冻结。 |
| P1-10 TCP封顶3M、起步800k | 不做统一硬编码 | TCP确有队头阻塞风险，但8Mbps上限不等于实际持续发送8Mbps，更不能证明必然秒级排队。应用已有按路径的起步档及拥塞保护；固定3M会限制健康60Mbps链路画质，未知路径固定800k也会拖慢好链路起画。需按实际TCP中继测得的排队曲线决定，而非按协议名一刀切。区域部署另见P2-15。 |
| P1-11 关键帧10秒3次 | 采用应用刷新请求预算 | 一个原生clearFrame epoch只主动请求一次关键帧，后面的forceFrame通常是供编码器细化的输入，并非每次都强制关键帧。限制和合并应用请求，实际编码关键帧另计；不拦截远端解码恢复的PLI/FIR、原生重启等必要关键帧，不能称为整个WebRTC的全局关键帧硬上限。 |
| P2-12 DEFAULT刷新率提示 | 暂不切换 | Android文档说明这是帧率提示，系统会综合多个Surface选择兼容刷新率，可能选倍频；FIXED_SOURCE不等于强制整机30Hz。当前渲染的是远端视频，已有EGL/VSync调度。在120Hz真机上做DEFAULT/FIXED_SOURCE对照后，才有依据选方案。 |
| P2-13 补诊断 | 采用可准确获取部分 | 增加QP、bpp、关键帧、两类尺寸变更和应用刷新请求。输出格式调用不是MediaCodec重启；500ms采样的编码尺寸计数也可能漏掉采样间的快速变化，因此明确标注。QP未知时保留未知；不把阶段均值相加、RTT除2或现有ACK冒充输入到显示延迟。实际重启次数、端到端P50/P95仍需原生事件与双机标定。现有sendDelay/jitter是区间均值，也不是原始逐帧/逐包P95。 |
| P2-14 可选60fps | 暂不采用 | 保留用户已选的30fps。仅“直连且BWE>4Mbps”不足以证明88%/90%像素下能稳定60fps；还需编码、解码、显示和额外带宽余量。没有真机结果就增加入口，容易再引入不稳定节拍。 |
| P2-15 多区域TURN/P2P | 部署候选，本次不执行 | 原理上更近中继可能缩短传播时延，但要先知道两端地区、实际选中候选和区域RTT，无法从清单确定能省50–150ms。现有ICE已支持直连与TURN回退，多加STUN也不能保证穿透对称NAT。新增服务器涉及区域、资源与运维，本文不能代替这些条件；本次未改服务器配置或部署。 |

## 清单中需要纠正的论据

1. 80%/88%对照版已没有交互降分辨率；0.3.30普通版的精修也不会绕过90%输出计划。不能再把“精修必然变原生尺寸”作为当前故障结论。
2. `setOutputFormat`调用、提交帧尺寸变化、编码输出尺寸变化、MediaCodec configure/restart是不同事件。新增前两类可观测计数，不能冒称实际重配次数。
3. 24次补帧不等于24次关键帧；原生每个请求epoch只取一次关键帧请求，真正编码关键帧由RTC统计独立观察。
4. “只用QP与实际码率确认”不够：编码器统计不能证明对端解码并完成显示。两端形状、采样新鲜度、解码与swap进度校验保留，QP是附加质量信号。
5. 目标QP≤30、bpp≥0.09、≤1.5秒清晰和P95≤250ms可以当测试目标，不能从静态代码推出已经达成；不同编码格式的QP也不宜直接横比。

## 验证范围与复测建议

自动检查覆盖：大屏十次交互输出尺寸不变，旧保护档不改像素；未知QP、首帧丢弃与接收反馈能在12次输入内完成；原生提前完成后不继续强制补帧；播放恢复立即取消静止补帧；BWE缺失/低估/高估边界；不受自身预算递归乘低；刷新滚动限额、会话重置；严重排队500ms与普通尖峰迟滞；QP/bpp的缺失、静止、变尺寸和计数器重置。

构建及实际测试数量、签名和输入摘要见 `../artifacts/BUILD_0.3.31.json`。本次不改AAR/原生库、不部署后端、不安装或操作用户手机。软件测试不能替代OPPO Android11/vivo Android16实测，不宣称P95下降多少。

建议同一对手机、页面、音频设置，分别在直连、UDP中继、TCP中继比较0.3.30与0.3.31；记录十次滑动、停手文字及十分钟视频。限速2Mbps、5%丢包、80ms抖动的验收需要受控测试链路。通过240fps相机对准两端测输入到显示，诊断记录尺寸变更、QP/bpp、关键帧、排队/缓冲、冻结数。保留原清单的目标值作为待验证标准。

## 参考定义

- [Android帧率提示文档](https://developer.android.com/media/optimize/performance/frame-rate)：系统选择兼容显示刷新率、倍频及FIXED_SOURCE用途，不保证获得请求刷新率。
- [W3C WebRTC统计定义](https://www.w3.org/TR/webrtc-stats/)：qpSum/framesEncoded为区间QP均值来源，keyFramesEncoded/Decoded为编码/解码关键帧统计，totalPacketSendDelay与jitterBufferDelay为累计量，必须取差分；QP可缺失、依编码格式解释。
- 本地证据：`ScreenContentVideoPlan.kt`、`QualityStats.kt`、`VideoRecoveryProbe.kt`、`ClearFrameRefresh.kt`、`SessionMedia.kt`，以及 `webrtc-patch/library/org/webrtc/SimpleRcFrameRefresh.java`、`SimpleRcEncoderQueue.java` 和现有硬件视频补丁。
