# 0.3.11 低延迟与流畅度优化

本版在 0.3.10 触控修复之上，调整编码队列、按实际媒体线路分配视频预算，并把接收端压力反馈给发送端。目标是减少积压，网络或设备吃紧时先降低负担，再逐步恢复。实际延迟和流畅度仍需两台手机测试。

## 本次修复

- 移除 MediaCodec 的 `KEY_MAX_FPS_TO_ENCODER`，保留源输出及 RTP 发送端限帧。该参数会自行丢弃 Surface 输入，上层的输入/输出元数据队列却仍等待对应结果，存在队列堵满风险。
- 编码队列优先保留 2 帧；需要第三帧才能出结果的编码器，按配置帧率等待 50–150ms 后放行第 3 帧，替代固定 200ms。编码器重建时重置队列；不任意丢弃已编码参考帧。
- GPU 帧率按完成换缓冲的帧计数，耗时计数在同一锁内取样，避免把绘制提交算成显示完成，或读出伪造的延迟尖峰。保留最新单帧渲染与过期待显示帧丢弃。
- 画质降低时直接减少采集 Surface 和源输出像素，发送器的缩放系数保持 1，避免重复缩小。Android 10/11 重建 VirtualDisplay，Android 12 及以上调整原有 VirtualDisplay；不重复使用 Android 14 的录屏授权创建新投影。
- 线路类型来自选中的 ICE 候选对。LAN 仅在 host/host 地址匹配本机真实网卡前缀时确认；不通过“私网地址”猜测。TURN 的 TCP/TLS 接入腿必须结合双方各自的本地统计，不能用 remote.protocol=udp 冒充全程 UDP。
- 媒体/控制线路变化（包括旧路径→暂时无路径→新路径）清理旧基线，媒体线路变化同时清除旧接收反馈。

## 自适应策略

| 实际媒体路径 | 起始视频预算 | 视频上限 | 可用带宽预算比例 |
| --- | ---: | ---: | ---: |
| LAN / UDP P2P | 2Mbps | 4Mbps | 80% |
| TURN UDP，所有中继接入腿已确认 | 1.5Mbps | 4Mbps | 75% |
| 直连 TCP / TURN TCP、TLS / 未确认的中继 | 1Mbps | 2Mbps | 70% |

上述比例之后还预留音频 128kbps、控制 192kbps。它们是发送上限与策略预算，不是承诺的实际码率。保持 ICE 自动选路及 UDP/TCP/TLS 回退；没有强制中继或禁用兼容线路。

起始 30fps，长边最多 1280；只有网络与发送/接收设备持续提供健康统计，才升到目标 60fps。拥塞或处理压力下分辨率按 1、1.5、2、3 倍降档；最低预算 150kbps、目标 20fps。发送排队、RTT 相对增长、丢包、接收缓冲、编码/解码/GPU 等分别判断。纯 GPU 压力降低像素与帧率，不反复削减网络码率。

媒体统计与反馈每 500ms 更新；恢复证据至少间隔 750ms，恢复清晰度还需连续健康样本与预算余量，防止忽清忽糊。调参失败会重试。发包排队均值和接收缓冲均值取本次采样增量，缺测不会与旧分母混算；诊断耗时不等于端到端画面延迟。

## 用户测试

两台手机覆盖安装 `../artifacts/SimpleRC-0.3.11-debug.apk`，在“诊断与策略”选择“新策略”，结束旧会话并重新连接。

1. 同一 Wi-Fi：观察媒体路径是否确认 LAN，连续滚动、拖动和快速点击，再旋转屏幕。确认滑动与点击不变成长按、坐标不偏、旋转后画面恢复。
2. 不同网络：先看实际媒体路径，再观察 P2P 或 TURN 的表现。NAT 和防火墙决定能否直连，不能仅凭两端能上网认定 P2P。
3. 中继：分别记录诊断实际显示的 UDP 或 TCP/TLS；连续滚动 1–2 分钟，观察卡顿次数、冻结时间增长、发送排队与接收缓冲。没有出现某种线路就标记未测，不假定已覆盖。
4. 弱网与恢复：切换网络或制造正常网络竞争，观察是否先降低画质/帧率并保持响应，恢复后逐渐提档。静止屏幕低帧率本身不代表故障。
5. 最后开内部音频，确认听感、停播与画面同步。反馈时保留两端诊断值、实际线路、手机型号和问题发生的操作；RTT、ACK 与各阶段耗时都不能直接充当端到端延迟。

本版未改 WebRTC 原生 jitter-buffer/pacer 实现，当前 Java API 也没有直接的 playout-delay 调节接口。跨地域传播、TCP 重传阻塞和设备硬件能力仍有下限，不能承诺所有网络零卡顿。
