# 有界试升、失败回退与静止文字精修（0.3.23）

## 修复的恢复缺口

0.3.22的普通恢复依赖持续至少12fps的四阶段节奏，以及完整的设备成本证据。真实静止、低帧率视频、部分统计缺失时，旧保护档可能长期不恢复。本版保留原有健康路径，同时增加可回退的小步试升，不把统计缺失自动等同于性能不足或恢复成功。

所有操作仍不直接压到低清，继续优先最高30fps的流畅与低延迟。正常请求90%尺寸、最长2400，直连/UDP最多16Mbps、TCP最多8Mbps的路径上限保持；并非固定发送这些流量。

## 小步试升

- 持续画面恢复受阻约8秒后，可在链路仍可观测、无明确积压/设备压力时试升。每次边长最多约增加12%，码率预算最多增加10%，受原路径上限约束，不直接拉满。
- 每次试升从开始计时，2.5秒内必须验证。目标参数未应用、接收验证超时、处理变慢、网络排队或吞吐恶化，撤回临时设置；原安全档和新的压力退档继续生效。
- 新操作优先，立即撤回正在进行的试升；尺寸、路径、会话变化隔离旧试验。成功后把部分恢复结果提交为新档位，可继续渐进恢复，不要求恢复值正好落在旧离散档。
- 失败后按10/20/40秒退避，最长60秒，滚动一分钟最多3次失败试验；成功的后续试验也有间隔。无无限补帧、无每个统计回调重复试升。

## 接收端确认

解码回调只记录累计帧数和尺寸，不保留VideoFrame、不读取像素。控制端同时回报原生渲染器完成的交换缓冲次数。这些数据不依赖WebRTC是否提供每帧成本字段，因此部分指标未知时仍可进行有限验证。

试升需要目标尺寸匹配、接收解码与显示提交计数实际前进、两次不同序号的反馈，以及至少1秒观察。持续画面的计数须跟上其实际源节奏，静止画面使用有界精修计数；不把完全没有反馈当成功。反馈原始采样时间必须晚于参数应用，重复、过期、旧尺寸和无显示进度的消息不能确认。反馈优先实时通道，拥塞或不可用时才回退可靠通道。

这里的显示计数确认GPU提交完成，不证明屏幕扫描输出，也不代表测得真实端到端延迟。

## 静止文字

真实生产帧停下超过300ms且无操作后，静止保持一段时间可进入文字精修。先恢复已受保护的档位，再允许典型1080×2400手机从正常约970×2160试到原屏1080×2400；大屏仍受长边2400限制。只有静止精修临时优先保分辨率，新操作或生产帧恢复后切回通常的保帧率策略。

普通静止/低帧率试验最多补6帧；文字精修最多8帧、间隔200ms；回退最多补2帧。持续视频用自然到达的帧完成试验，不为试升额外制造重复帧。清晰关键帧及后续精修使用既有本地编码确认：匹配尺寸、关键帧后多帧和QP门槛，编码器不提供QP时走8帧上限回退。编码器没有Java确认钩子时，需要至少8个匹配接收尺寸与显示提交进度才使用有限回退证据。

尺寸变大本身不单独宣称完成文字精修。真实链路或设备压力、无法验证精修时撤回；不会为了清晰度持续堆积高分辨率帧。

## 诊断与边界

被控端状态会同步到控制端的调试窗口，包括缺少接收反馈、真实帧节奏不足、设备余量不足、目标尺寸未解码、等待编码精修、正在试升、超时回退、重试等待秒数和达到正常目标。诊断文本变化才更新状态，避免高频重复刷新界面。

若接收反馈长期完全中断，程序仍不能安全确认高清，只能有界试验、回退并继续显示原因；不存在“到时间无条件拉满”的规则。低帧率和指标缺失不再永久没有试升机会，但不保证不满足链路/设备条件时强制恢复高清。

回归覆盖小步限幅、低帧率/缺成本验证、缺反馈、错误尺寸、旧采样、重复反馈、没有显示进度、超时、压力首样本回退、失败退避、静止原屏请求、编码精修门槛与无钩子回退、用户操作/路径/旋转隔离和动态部分恢复。构建与签名回执见 `../artifacts/BUILD_0.3.23.json`。

WebRTC AAR与0.3.22逐字节相同，库未重建，沿用相同AAR的0.3.20调度/采集桩/队列回执。未安装或测试手机，未部署服务端。两端覆盖安装 `../artifacts/SimpleRC-0.3.23-debug.apk`，选择“新策略”后重连；实际字体、帧率及延迟仍需双机确认。
