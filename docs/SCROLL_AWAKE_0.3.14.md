# 0.3.14 滑动卡顿与屏幕保持

本轮依据用户提供的 38.68 秒录屏检查两端滑动时的停顿，并补充“应用打开及连接期间不自动息屏”。支持范围仍为 Android 10 及以上、四种 CPU 架构。视频的 720×1592、663 帧是录屏文件属性，不能当成远控链路的实际帧率或端到端延迟。

## 修复与整理

- 编码器原始输入上限从两帧恢复为上游的三帧。原两帧策略在可正常流水处理、输出延迟 90ms 的 30fps 编码器模型中只能接收 40/60 帧，而且每次输出重置堵塞计时，兼容回退一直不生效。三帧策略允许该模型接收全部 60 帧；60fps、45ms 延迟的对应场景也通过。队列仍有界，不更改压缩帧的参考关系。
- 显示队列仍只保留最新一帧、合并唤醒任务，移除“最新画面等候超过 150ms 就直接丢掉”的规则。这样滑动末帧即使遇到一次较长的显示阻塞，也会在恢复后绘制，不必等待下一张画面。等待、绘制和交换耗时继续计入诊断。
- 将估计带宽对应的画面像素预算与发送码率上限分开。`availableOutgoingBitrate` 是 WebRTC 的当前带宽估计，不能每次乘余量系数后再次写回上限，形成自我压低的反馈。真实丢包、网络 RTT 增长、发送/接收积压仍触发有冷却时间的退降；健康且估计贴近自身上限时逐步恢复探测空间。
- 网络适应仅使用 ICE 网络 RTT。应用 PONG 在两端主线程处理，滑动时主线程变忙不能直接被视为网络拥塞。PONG 继续用于时钟校准与诊断。
- RTCP 丢包按最新接收报告时间消费一次，重复、倒序报告不再被每个统计周期重复用于降码率。
- 提取 `FrameCadenceEvidence`，用源、编码、解码、实际显示四段的帧计数差值判断持续吞吐。至少连续 4 秒达到当前目标的 80%，才累计提高负载的证据；静置、零帧、缺测、过期反馈、会话或路由变化不能用于升级。默认从 30fps 开始；60fps 出现处理压力时先退回 30fps，持续压力再缩小发送画面，减少频繁重启编码尺寸。
- 保留 0.3.13 的完整屏幕采集、输出尺寸分离及旋转 Surface 修复，网络自适应不重新缩小系统投屏范围。
- 两端打开应用即设置窗口保持亮屏；连接、确认、共享或控制期间服务也保持显示。停止、切换角色、会话结束后释放相应资源。手动锁屏不会被自动点亮或解锁；单纯退出到后台且未连接的待机只维持待机服务，不强制屏幕常亮。

检查后又修正了两个恢复边界：自身码率上限造成的 bandwidthLimited 不能永久阻止画质恢复；网络恢复导致的升分辨率也必须具备真实帧节奏证据。未改变现有手势分段长度或抢先并发注入，继续保留误长按与触点释放保护。

## 验证与实际测试

底层组件与客户端的最终结果分别记录在 `../webrtc-patch/VIDEO_BUILD_0.3.14.json`、`../artifacts/BUILD_0.3.14.json`；构建输入冻结清单为 `../artifacts/SCROLL_AWAKE_INPUTS_0.3.14.json`。队列测试直接加载新 AAR 的实际 helper 类，旧 AAR 能被同一吞吐测试检出；投屏回归运行实际 capturer Java 源码与系统行为桩。这些均不代表已在真实硬件上完成验证。

两端覆盖安装 0.3.14，断开旧连接后重新连接；“诊断与策略”使用“新策略”。建议按以下顺序验证：

1. 未连接时分别把应用留在前台，超过原系统自动息屏时间；连接后控制端留在远控画面、被控端打开其他应用，再等待同样时间。
2. 先在被控端本机连续快速滑动列表，再由控制端滑动同一列表；对照正常播放视频，确认滑动与松手后的最终画面持续更新、完整显示。
3. 重复短滑、长滑、快速上下切换、停住再滑及横竖屏切换，确认没有误长按、局部裁切或松手后残留触点。
4. 分别检查同一 Wi-Fi、跨网直连和中继条件；如仍有卡顿，查看两端诊断中的采集、发送、解码、显示帧率、队列、网络 RTT 和实际路径，以区分下一处瓶颈。

本轮没有安装或操控手机，也没有测得真实双机延迟；不承诺所有厂商后台策略、散热限制与网络下永不卡顿。后端协议和服务代码未改动，本轮无需服务器更新。

## 核对依据

- [WebRTC candidate-pair 统计来源](https://webrtc.googlesource.com/src/+/refs/heads/main/pc/rtc_stats_collector.cc)：availableOutgoingBitrate 来自 call send-bandwidth 估计。
- [WebRTC 发送带宽估计上限](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/goog_cc/send_side_bandwidth_estimation.cc)：估计目标受配置上限约束。
- [W3C remote-inbound-rtp 统计](https://www.w3.org/TR/webrtc-stats/#dom-rtcremoteinboundrtpstreamstats)：timestamp 对应接收报告到达时间。
