# 导航与实际滑动的画质切换（0.3.20）

## 源码确认的问题

返回、主页、任务切换原来只派发系统动作，没有通知视频策略，因此按返回引起的动画不会立即走交互档。触控则相反：DOWN/MOVE每次成功提交都续期压缩，坐标不动的40ms心跳、长按和点击也会触发；加上500ms最小停留和700ms输入寿命，容易造成晚到后才变糊、停止操作后仍模糊。以上是源码问题，未从用户设备统计确认所有实际成因。

## 修改

- 返回、主页、任务切换在等待原生手指释放后、实际执行系统动作前才启动350ms交互脉冲。排队时不提前降画质；持续出帧不能续期脉冲。系统动作失败仍最多影响这350ms，不影响输入ACK的真实结果。
- 滑动通过独立VIDEO_MOTION提示驱动画质，不再从触控心跳推导。累积位移至少2个远端像素才算移动，提示间隔至少16ms；长按不动、静止心跳和普通点击不触发低清，长按后真实拖动仍触发。
- 提示优先走无序不重传的实时通道，在可靠DOWN之前发送；实时通道不可用时回退可靠通道。提示仅改变视频策略，不能注入输入，也不推进输入排序序号。
- 提示携带原始事件时间，寿命220ms包含网络年龄和时钟不确定度。迟到提示不能从收到时重新续满；结束提示双通道发送，80ms以内收尾，结束水位阻止迟到的同一手势重新打开低清。缺失结束消息仍在220ms内过期。
- 取消交互态500ms最小模糊停留。MEDIA/STILL的500ms迟滞、真实帧500ms统计窗口、连续高速1秒媒体确认与300ms静止判断保留；媒体和静止使用相同清晰分辨率，所以媒体识别不会改变清晰度。
- 正常输出约为原屏每边85%，长边最高2160；典型1080×2400目标为918×2040，旋转保纵横比。交互仍为长边360、最高350kbps；捕获Surface保持原屏，继续最高30fps及VSync调度。清晰预算仍最高8Mbps，TCP2Mbps，实际由WebRTC控制。
- 独立CPU保护不再仅因残留的cpu标记连续缩小画面。要求实测编码、解码、绘制或排队超标，或cpu标记同时伴随源帧率≥24、发送<18的持续吞吐缺口。连续三次压力才降一级，原恢复与冷却要求保留。
- 保留清晰关键帧及有界多帧精修；不新增逐帧CPU像素分析或重型软件编码。
