# 激进交互压缩与停手文字恢复（0.3.19）

## 修改的具体问题

0.3.18在交互态使用960长边，媒体态每边只有原屏75%；系统持续提交新纹理时，即使用户在读静止文字也可能留在媒体态。网络/处理安全档又要求持续真实帧节奏才能恢复，静止时可能长期保留旧低分辨率。应用请求完整尺寸也不能保证库内部已经解除交互降级。旧清晰补帧只等待一个关键帧，最多4次输入；粗糙的首个关键帧、编码尺寸按16像素对齐、缺少后续精修，都可能使“请求了清晰”与“真正恢复细节”不一致。

以上是源码中确认的限制，不代表已从用户手机统计确认所有实际成因；真实字体与耗时仍需双机测试。

## 新策略

交互期间目标长边360、码率上限350kbps、帧率上限30。1080×2400屏幕的目标从432×960降为162×360，编码像素量约为上版七分之一。网络或设备仍可使实际帧率/码率更低。继续使用纹理缩放和现有硬编，不换重型软件编码器，不增加逐帧CPU读图、像素差分或运动模糊。

抬手后的200ms尾巴和状态500ms最小停留继续生效。媒体态与静止态都请求完整原屏尺寸，不再因为持续出帧而固定在75%；切换到MAINTAIN_RESOLUTION，优先保留文字细节，资源不足时实际帧率可能降低。最高30的采集与VSync调度保持，30是上限而非强制真实帧率。

旧交互/弱网缩放档不直接限制非触摸画面的像素。清晰阶段采用独立DetailProtection：只计算非交互阶段的新压力证据，连续3次编码、解码、绘制或额外排队超标才降一级，至少间隔3秒，比例为1、1.25、1.5、2、3。真实CPU吃不消就退档，不为清晰度反复强顶满分辨率；只有持续实测余量才逐级恢复，未知、重复、间隔过长的指标不能证明恢复能力。诊断状态会明确显示CPU保护降级。

非触摸阶段正常路径的发送预算最高8Mbps，中继TCP仍最高2Mbps；minBitrate保持0，实际由WebRTC拥塞控制决定。检测到真实RTT/丢包/发送积压/抖动异常时，清晰阶段也继续使用收紧后的安全预算。交互时主动350kbps限流产生的低带宽估计，不再将清晰阶段的应用上限永久锁在低值。预算不是固定发满8Mbps，也不是保证所有网络都清晰。

## 有界精修

静止或交互结束后，先应用完整尺寸和清晰预算，再请求关键帧并允许后续预测帧逐步修复细节。最多补12次，间隔至少150ms；新触摸、旋转、关闭继续取消旧请求，不建立无限补帧循环。重复纹理仍不计入真实采集帧率或媒体判断。

硬编输出按真实编码尺寸及新时间戳核对，允许不超过16像素的编码对齐误差，不能用低一档分辨率冒充。关键帧之后至少4个匹配尺寸输出，且最后一次QP不高于28才确认本地精修；编码器不提供QP时使用8个输出的有界回退。高QP的粗糙关键帧不会单独宣称完成。软件编码回退仍有补帧，但Java硬编确认钩子可能不执行；所有情况都受12次上限约束。

该确认只描述本地编码，不证明远端已显示，也不意味着无损字体。H.264仍有损，无法把源码检查或模拟测试当成主观清晰度验收。

## 验证及使用

新增回归覆盖：持续出帧的文字也请求原屏、旧交互缩放不锁清晰画面、强压交互像素/预算、真实CPU压力退档、短时重配置尖峰不误退、未知/重复/旧指标不误恢复、清晰预算真实拥塞与TCP限制、16像素对齐、低档/旧关键帧拒绝、粗糙关键帧需精修、12次补帧上限。

AAR仍从固定上游及三份补丁重建，四ABI原生库和25个内部音频类与0.3.18一致；保留16项调度器行为检查、10项capturer行为桩与8项队列回归。运行回执和最终APK校验见 `artifacts/BUILD_0.3.19.json` 与 `webrtc-patch/VIDEO_BUILD_0.3.19.json`。

两端覆盖安装 `artifacts/SimpleRC-0.3.19-debug.apk`，选择“新策略”后重新连接。后端无变化，无需部署。本轮没有安装或测试手机；请重点对比滑动中响应、停手后细字逐步变清、视频播放中触摸后恢复及连续滚动时温度/CPU压力。若仍看不清，需结合实际编码尺寸、码率、编码器、状态和CPU保护标记继续定位。
